# Phase 46 Addendum — GitHub Capture Source Integrity Hardening

## Status

`AUTHORITATIVE ADDENDUM`

This document extends `phase46-github-observation-explicit-capture-provenance.md` after the implementation audit identified an important distinction:

```text
owner-readable capture_source_refs row
!= provider-verified GitHub provenance
```

The base Phase 46 decision remains authoritative except where this addendum makes the verification requirement stricter.

---

## 1. Why the additional proof is required

`capture_source_refs` is protected by owner-centered RLS and is intentionally private, but an authenticated Project owner can still issue allowed INSERT operations against owned source tables.

Therefore row existence alone cannot prove that the source identity was obtained through BuildMap's server-side exact GitHub re-read.

Phase 46 must distinguish:

- source rows that BuildMap server code created after exact provider verification, and
- source-shaped rows that merely satisfy database ownership/RLS constraints.

This is an application integrity boundary, not a transfer of authority to GitHub.

---

## 2. `source_proof`

Migration 18 includes:

`capture_source_refs.source_proof`

Properties:

- generated by BuildMap server code only during the product Capture flow,
- HMAC-based using the existing server-only GitHub App state secret,
- never exposed as a public-safe field,
- not a GitHub credential,
- not an installation access token,
- not sufficient to call GitHub APIs.

The proof seals the provider source identity tuple:

```text
rough_note_id
project_link_id
source_type
external_source_id
canonical_url
```

The proof does not replace RLS, Project ownership validation, exact provider re-read, or database consistency triggers. It is an additional defense that allows later application reads to distinguish verified source identity from unverified table state.

---

## 3. Capture-time rule

After the Builder explicitly selects `Capture as evidence`:

1. BuildMap validates the Project and GitHub read binding.
2. BuildMap re-reads the exact PR/Release from GitHub.
3. BuildMap creates the Rough Note.
4. BuildMap computes `source_proof` over the verified source identity and new Rough Note ID.
5. BuildMap inserts the immutable `capture_source_refs` row.

If source provenance insertion fails, the newly-created Rough Note is not treated as a completed Capture and is archived by the compensation path.

---

## 4. Read-side trust rule

Application surfaces must not treat a GitHub `capture_source_refs` row as verified provenance solely because it exists.

For GitHub source rows, the application verifies `source_proof` before using the row as verified source provenance.

Current protected read/retry surfaces include:

- Builder Evidence trace,
- failed AI draft retry mode selection,
- duplicate-source Capture handling.

An invalid or unverifiable proof must not be repaired by:

- title similarity,
- URL similarity,
- Rough Note text,
- AI inference,
- another repository/source guess.

The Evidence surface reports an integrity problem instead of rendering that row as verified GitHub provenance.

---

## 5. Environment degradation

Proof verification requires the server-only GitHub App state secret.

If that configuration is absent, BuildMap core remains usable, but GitHub provider provenance cannot be positively verified by the read-side.

The application must fail closed for GitHub-specific evidence operations rather than treating unverified provider rows as trusted.

This does not make GitHub or its configuration a dependency of ordinary Builder Capture, Feedback evidence, Decision history, or public Project Map reads.

---

## 6. Public and authority boundaries

`source_proof` remains Builder-private implementation integrity metadata.

It must not be surfaced through Scout/Public views.

The proof establishes only that BuildMap's server-side GitHub Capture path verified and sealed the external source identity at Capture time.

It does not mean:

- GitHub approved a BuildMap Decision,
- GitHub owns the Decision identity,
- the external source is a PIE Evidence object,
- a source row can bypass Builder Review,
- the captured observation is automatically correct as a product judgment.

Official Decision authority remains with the Builder.

---

## 7. Schema clarification

The normalized Phase 46 `capture_source_refs` field set is therefore the base decision's list plus:

- `source_proof`

No other provider credential or raw payload field is authorized by this hardening.
